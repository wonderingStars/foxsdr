## Features and fixes, 2026-10-13

Three changes were made on 2026-10-13, after 0.99.75 was published: the display-range menu, the guard for the page grip's resize-corner id, and the reading of a Linux scan helper's closed pipe. The first answers a dislike from the field, the second a fatal crash report and the third two crash groups from one Linux session. They touch different parts of `src/gui/app_window.cpp` and `src/source/soapy_enum_proc.*` and applied together without a conflict.

**For the crash admin: type 0.99.76 as the fix release, and no earlier number, for these three groups.** The fatal crash group `crash cascade.exe @ ImGui::GetWindowResizeCornerID` holds report `D94CCD4584724FAC` (0.99.58) and report `DE3F72AAE6B69997` (0.99.75); it was marked fixed on 2026-10-01 with no release named, and the second report is the one that reopened it. The Linux enumeration groups are `862234B08B9FC33D` and `30BCD594C128766D` (0.99.73, six scan-helper deaths in one second from one session). 0.99.76 is the first release that contains either change, so a report of one of these signatures from 0.99.75 or earlier is not a regression and one from 0.99.76 or later is. The Linux half has not been run on Linux (below), so a 0.99.76 report from a Linux machine is the first real test of it.

**Right-click the spectrum or the waterfall to set the range of the picture yourself: the menu now ends with a Display block - Range: Automatic or Manual, a Floor and a Ceiling slider, and Reset display to defaults - and the strength key says MANUAL while your own window is in force; hold the pointer still over either panel for four seconds and a tip says that the right-click menu is there.** A French user on 0.99.75 with an RTL-SDR V4 wrote that "the spectrum and the waterfall are very milky, one cannot see the signals", and the owner's answer was to let people set it themselves, by right-clicking. The window was always adjustable - SYSTEM > Display > Min dB and Max dB - but that section has been folded until opened since 0.99.74, and nobody with a milky picture had a reason to open it. The two sliders in the menu are the same two numbers, so either place changes both, and nothing in the signal path changed. The menu is on the receiver's waterfall (the marker menu), on its spectrum (the trace menu) and on a patch Spectrum part's picture and trace, the same block each time, after the items that were already there.

What Automatic and Manual are, because the two views meant different things by "automatic" before there was a word for it: the receiver's spectrum and waterfall have always been drawn through one fixed window, -110 to 0 dB, unless the sliders moved it, and that window is Automatic; a patch Spectrum part fits its own window to every line it draws (the 20th-percentile bin, which is the noise, up to the loudest bin, never under 30 dB), and that is Automatic there. Manual is your floor and your ceiling on all of them together, so the spectrum's scale, the waterfall's colours, the strength key and every patch Spectrum part agree about what a colour means. The ceiling stays at least 10 dB above the floor, and the slider you are dragging is the one that stops. Reset display to defaults goes back to Automatic, forgets the pair, and returns the spectrum to its normal trace. The choice is saved as `waterfallRangeMode` (`"auto"` or `"manual"`) beside the `dbMin` and `dbMax` that have always been in `config.json` (the floor and ceiling Manual uses, kept while Automatic is in force); a file with no mode, from 0.99.75 or earlier, opens in Manual if its pair is anything but -110 and 0 and in Automatic if it is, so nobody's picture changes. The waterfall keeps the colours it has already painted, as it always has when the sliders moved: after a change the key says "APPLIES TO" the newest lines and a "RANGE CHANGED" rule crosses the picture. Display > Min dB and Max dB now show the window in force, make the range Manual when dragged, and clamp a typed value (ctrl-click entry could exceed the slider's bounds before).

The tip is the owner's: "when the mouse is over it for 4 secs". After four seconds of rest over the receiver's spectrum or waterfall, or a patch Spectrum part's trace or picture, a tooltip reads "Right-click to change the range and display", in place of the panel's usual gesture tip while the hand stays still. Moving more than 6 pixels, pressing a button, dragging the band, panning, opening the menu or leaving the panel puts it away, and it comes back after another full four seconds. One related fix: a range exactly 10 dB apart is now kept. The sliders always allowed it and the config loader refused it, so a range left there was thrown away, both ends back to -110 and 0, at the next start. The remote control's own range check still refuses a request that names both ends exactly 10 dB apart.

Verified on Windows with the real application. `test_display_range` (83 checks) pins the arithmetic: a sweep of 52,140 combinations of a pair and a moved end comes out in bounds and 10 dB apart every time, with the end that was not moved never touched; Automatic ignores the pair and Manual uses it; Reset forgets it; and a file's mode is read from its pair when it has no word. `test_hover_dwell` (133) pins the clock: not before 4.0 s, due at 4.0 s, a move, a press, a menu, leaving, ten seconds unasked and a bad clock each end the rest, and the spectrum's "not over me" does not undo the waterfall's. `test_config` (3,529) round-trips the new key, reads it from a pair when it is missing, wrong-typed or unknown, and sees it in `configsEqual`; its one old expectation, that a pair exactly 10 dB apart is reset, was wrong for the reason above and now expects the pair kept, with a new case a hair under 10 dB that is still refused. `test_display_menu_app` (108 checks, 23 runs of the real `cascade.exe`, 95 s) right-clicks the waterfall, the spectrum and a patch Spectrum part with the application's own input script and reads the UI census and the saved config: picking Manual and dragging Floor and Ceiling to 70% gave -59 / -14 in the config, on the strength key (with MANUAL) and on the spectrum's scale, all three the same two numbers; a ceiling dragged to 5% from -60 / -20 stopped at -50, and the floor then dragged to 95% stopped at -60; Reset from Manual with Peak hold gave Automatic, -110 / 0 and the normal trace; a restart in Manual showed -60 / -20 with MANUAL; the tip was not shown after 3.12 s of rest and was after 5.13 s, on the spectrum and on the waterfall; a right-click with the tip up opened the menu and took it away; a move left 1.64 s of rest and a press 1.20 s, not the old 5. Against the unchanged build the same test failed 34 of 70 checks (the steps that aim at the menu's items are skipped when the menu is absent), and deliberate breakages made the test named after each fail: fourteen one at a time in the arithmetic, the clock and the config, and three groups in the real application (the key's MANUAL, the spectrum's scale, the trace reset, the saved mode and the patch part's Manual removed together made 17 checks fail, the held button, the popup, the "over" test and the movement rule removed together 5, and the dwell cut to 0.5 s alone 7). The new words were seen by eye in screenshots of the real window, in English: the menu in Manual with the sliders at -59 / -14, the key reading "STRENGTH KEY - dB MANUAL", the menu in Automatic with its sliders greyed, and the tip. The right-click menu on the waterfall is now about 314 pixels tall, so low in the window it opens above the pointer; `test_freq_markers_app` clicked low in a patch part and was moved up to 5% down the picture for that reason, with its assertions unchanged.

Not fixed, and known: nobody has seen the reporter's screen, so whether a Manual floor cures that picture is a hypothesis. There was no screenshot and no bundle with the dislike, and the same reporter's 0.99.72 bundle logs seven theme changes in 43 seconds; Daylight Lab's colour ramp runs from a light colour at the floor to a dark one at the top, which looks milky by construction, and there is no waterfall palette to offer beside the range. No gamma or contrast control was added (the dB-to-colour map is a straight line into the theme's ramp and a gamma would reach `addLine`'s three callers and the strength key's own scale), and the spectrum's and waterfall's existing gesture tips still say nothing about the range, which the four-second tip now does. Nothing was tried on Linux or Android, in a theme other than "today", at an interface scale other than 100%, or with a real radio, the patch Spectrum part's menu was not looked at by eye, and the 6-pixel slop and the 10-second gap are choices, not measurements.

**FoxSDR no longer dies when a window is dropped into, or pulled out of, a dock node: the fatal `GetWindowResizeCornerID` crash reported on 0.99.58 and 0.99.75 is guarded.** The page grip in `AppWindow::beginPage` asked ImGui for its resize corner's id in every frame, and ImGui answers that by reading the dock node's host window, which does not exist yet in the frames after a window is dropped on another one (or is still being created for it). Report `DE3F72AAE6B69997` (0.99.75, from a machine that had opened the WEFAX window five minutes earlier, and probably the one whose user filed a bug that day saying that inserting a window at the bottom with the mouse does not work) faulted at `GetWindowResizeCornerID+0x1b`, which in a build of the same source is the load of the host window's id; the 0.99.58 report `D94CCD4584724FAC` has the same two frames. The id is now asked of one helper, `gui/page_resize_id.hpp`, that answers 0 when there is no window or no host to ask, and a lit grip is no longer decided by 0 meeting 0 (the first version of the guard would have lit the grip and turned the cursor into a resize arrow in every frame that nothing was hovered). A new test, `test_page_resize_id` (22 checks), builds the windows ImGui builds in those frames; before the guard it faulted with 0xC0000005 on the null window, on a docked window with no node and on a docked window whose node has no host, and with the guard it passes; the guard was removed in four ways and each turned a named check red. It also scans `src/` and fails if anything other than the helper calls ImGui's resize-id functions. Not reproduced live: the drop itself was not driven with a mouse, so that this is the report's path is a reading of ImGui's source and of the disassembly, not an observation. The application enables ImGui's docking but never creates a dock space over its main window (there is no `DockSpace` call in `src/`), so a page can be docked onto another page and not into the edge of the main window; that, read from the source and not tried with a mouse, is what this guards, and it is not an answer to the reporter's complaint that inserting a window at the bottom does not work.

**A Linux scan helper whose pipe has no reader is no longer filed as a crash, and no longer takes its driver out of the session's scans.** Reports `862234B08B9FC33D` and `30BCD594C128766D` (0.99.73) were six "crashes" from one Linux session in one second, every one exit `0x8D` = 141 = 128 + `SIGPIPE`, and the last blamed the `rtlsdr` driver alone, which put a working RTL-SDR on the do-not-ask list for the rest of the session. The helper now ignores `SIGPIPE`, writes through a function that learns of a closed pipe from the write itself and ends with its own exit code, 74, after finishing the walk; the parent reads 74, and 141 from a helper that did not ignore it, as a closed pipe: the scan is retried and swept and counted as before, but nothing is written to the crash directory and no driver is remembered. A real abort or segfault while the parent is listening is reported exactly as before, and a helper the parent timed out is still a timeout. Verified on Windows by 545 checks in `test_soapy_enum_proc`: the same scan run as a closed pipe and as a real death, whole-bus, retry and sweep, with 0 reports and nothing remembered against 1 report and 3 reports with the driver remembered; the old reading, put back, failed 12 of them. What a Windows run cannot show: the helper's own `SIGPIPE` handling and the 141 path are POSIX-only and were type-checked against stubs with GCC, not run, and the Linux run in CI is the check. What is also not established: the parent holds the helper's stdout open until it has reaped it, so a closed stdout was not the field's pipe while the parent was waiting; the helper's inherited stderr, or a socket in a vendor module, is the suspect, and `httplib::Server`'s constructor ignoring `SIGPIPE` for the whole process would make a helper started before the web server died where one started after did not. `docs/DIAGNOSTICS.md` lists the changed and new log lines.

The eight new interface texts (`Range: Automatic`, `Range: Manual`, `Floor`, `Ceiling`, `Reset display to defaults`, `MANUAL`, `Right-click to change the range and display`, and the three-line tip on the two Range keys) are in all 33 catalogues (`py -3.14 tools/i18n_keys.py`: 1976 keys, 1976 translated, 0 empty, 0 missing, 0 stale in each; before, 1968 translated and 8 missing in each), `src/core/lang_assets.hpp` was regenerated once with `tools/embed-lang.py`, and `test_i18n` (196,187 checks) and `test_i18n_glyphs` (487) pass. They are machine translations that nobody has read. `Floor` and `Ceiling` are the lower and upper limit in the sense the catalogues already give `FLOOR / CEILING` on the strength key, the `MANUAL` tag on that key is kept to one short word (an abbreviation in Greek, as `AUTO` already is there) because the key is not drawn at all when it would take more than 46% of the picture's width (its width in each language was not measured), and a patch's part is the word the catalogues already use for it. The two work packages together build in Release without an error (the build was run twice, because they add four test files), and the whole suite, 368 tests one at a time, passed 368 of 368 in 2,322 s.
