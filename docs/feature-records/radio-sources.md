## Part 1: R13 SDRplay low-IF choice, W4a diagnostic report model, W4c service restart over an injected SCM

Files: `src/source/sdrplay_if_mode.{hpp,cpp}`, `sdrplay_diag_report.{hpp,cpp}`, `sdrplay_scm_restart.{hpp,cpp}`, test `tests/test_sdrplay_ifmode_diag.cpp`.

**What existed (verified in this tree).** `sdrPlayRatePlan()` (sdrplay_source.cpp) is zero-IF only since 0.99.44: two RSP2 field logs showed a low-IF 6 MHz plan delivering 6 MS/s where 2 MS/s was expected (the log lines are quoted there). The SDRplay probe (sdrplay_probe.cpp, stepIfModes) already holds the low-IF combinations transcribed from the API specification section 3.15. The tree also already has an elevated cmd.exe service restart (`SdrPlayServiceRestart`) and a probe report; W4a and W4c here are the two things asked for that it does not have: a plain report model + formatter, and a direct SCM restart with an injected interface.

**What was built.**
* `SdrPlayIfMode {ZeroIf, LowIf}`, `sdrPlayRatePlanForMode(rate, mode, plan)`: ZeroIf forwards to `sdrPlayRatePlan` unchanged (the default; `sdrplay_source.cpp` is untouched). LowIf offers 62.5k, 125k, 250k (fs 2 MHz, IF 450, BW 0.2), 500k, 1M, 2M (fs 2 MHz, IF 450, BW 0.6), 3M (fs 6 MHz, IF 1620, BW 1.536), 4M (fs 8 MHz, IF 2048, BW 1.536), 8M (fs 8 MHz, IF 2048, BW 5.0); every other rate is refused, never guessed. Output = fs / decimation.
* `sdrPlayLowIfRateVerdict(plan, measuredHz)`: classifies a measured stream rate as AsPlanned, DeliversAdcRate (the 0.99.43 field behaviour: within 2% of fsHz while decM != 1) or Other. The wiring lane must run it on the first real low-IF stream and refuse low-IF on a mismatch.
* `SdrPlayDiagReport` + `formatSdrPlayDiagReport`: API version/path, service summary, device list (model from hwVer, serial masked to the last four characters, tuner, RSPduo mode, in-use flag), last error and step.
* `restartSdrPlayServiceVia(ScmInterface&, name, limits)`: query, stop if not stopped, wait for Stopped, start, wait for Running; results Restarted, AccessDenied (Windows error 5, sentence says administrator rights), NotInstalled (1060), StopTimedOut, StartTimedOut, OtherError(number). `WindowsScm` wraps OpenSCManagerW / OpenServiceW / ControlService / StartServiceW / QueryServiceStatusEx (CONNECT, QUERY_STATUS, START, STOP rights only). `restartSdrPlayServiceNow()` is called by nothing and by no test.

**Specification, corrected after part 6.** The SDRplay API specification v3.15 IS readable, at https://sdrplay.com/wp-content/uploads/2026/04/SDRplay_API_Specification_v3.15.pdf (found through https://www.sdrplay.com/api/; the re-check had a wrong address), and was read on 2026-11-11: the low-IF table above was checked row by row against its "Conditions for LIF down-conversion" list and every row is permitted by it (it allows more, for example 8.192 MHz and BW 0.3). The part 1 commit message and this paragraph first said the PDF was unreachable; that is superseded. The specification still says nothing about what rate a low-IF stream delivers. **UNPROVEN.** Whether low-IF takes effect on a real RSP, and what rate it delivers, is unproven (no RSP). The real SCM wrapper compiled but was never run; the service was never touched.

HAND-OFF (wiring lane): add a persisted setting `sdrplayIfMode` ("zero-IF" default | "low-IF"); in SdrPlaySource replace the `sdrPlayRatePlan` calls with `sdrPlayRatePlanForMode(rate, mode, plan)` and use `sdrPlaySupportedRatesForMode` for the rate list; after start in low-IF measure the delivered rate and call `sdrPlayLowIfRateVerdict`, falling back to zero-IF on a non-AsPlanned verdict. ## Part 2: R4 SoapyRemote client (shared network-source base)

Files: `src/source/net_sample_source.{hpp,cpp}` (the base class every network source of this lane shares, plus `UdpTransport`), `soapy_remote_protocol.hpp` (codec), `soapy_remote_source.{hpp,cpp}`, tests `tests/test_soapy_remote_source.cpp`, `tests/src_test_net.hpp` (loopback helpers shared by the three network tests), thread-inventory row `src/source/net_sample_source.cpp` (R_DRIVER, one reader thread) in `tests/thread_inventory_rows.inc`.

**Documents.** https://github.com/pothosware/SoapyRemote: `LICENSE_1_0.txt` opened first (first line "Boost Software License - Version 1.0 - August 17th, 2003"; README: "Use, modification and distribution is subject to the Boost Software License, Version 1.0"; every source file carries `SPDX-License-Identifier: BSL-1.0`), so the sources were read (raw text fetched to a scratch folder outside the repository, read only, nothing built or linked): `common/SoapyRemoteDefs.hpp` (numbers), `SoapyRPCPacker.{hpp,cpp}`, `SoapyRPCUnpacker.{hpp,cpp}` (message layout), `SoapyStreamEndpoint.{hpp,cpp}` (datagram header, ACK), `client/Settings.cpp`, `Streaming.cpp`, `Registration.cpp`, `ClientStreamData.cpp` (call order, arguments, sample conversion). Master at 2026-11-11, RPC version word 0x000400. The format is written out in the header of `soapy_remote_protocol.hpp`.

**What was built.** Connect by address (default port 55132, TCP control), MAKE with the user's device args plus the `soapy_remote_no_deeper` key, native stream format and full scale, rates, frequency range, antennas, gains and gain ranges, gain-mode and frequency-correction flags; RX stream on channel 0 over `tcp` (DEFAULT: deliberate, a udp stream needs the server to reach this machine) or `udp`; flow-control ACKs; CS8, CU8, CS16 and CF32 to complex float; setFrequency, setSampleRate (snapped to an offered rate), setGain (clamped to the range), gain mode, antenna, correction; ACTIVATE/DEACTIVATE on start/stop; CLOSE_STREAM, UNMAKE, HANGUP on close. Discovery is left out. CS12, multi-channel streams, log forwarding, hardware time and TX are not built.

**Design points worth knowing.** The stream sockets are read in 200 ms slices and a TCP datagram is reassembled across slices (a header split by a pause loses nothing: `testSplitHeader`), because `shutdown()` alone did not wake a parked receive in this test against a server that keeps its end open (the first run abandoned a reader for 2.5 s; found by the silent-server close test). A streaming source whose server goes silent for `max(3, timeout/200 ms)` slices latches a fault ("the radio server stopped sending"); an idle (not activated) source tolerates silence. Stream status datagrams TIMEOUT/CORRUPTION/OVERFLOW/UNDERFLOW (-1/-3/-4/-7) are counted as dropped, any other negative code is fatal. The sample conversion follows the reference client's: CU8 is `(u - 127) / scale`, the others `v / scale` (scale = the server's reported full scale).

**UNPROVEN.** Against a real SoapySDRServer: everything on the wire. The stand-in (`tests/test_soapy_remote_source.cpp`) has its own packer and parser with literal numbers, written from the same reading, so it cannot show the reading was right; it did catch two slips of mine in the first run (the call number is a typed INT32; every STRING has its own type byte). Not read, so not built: the CS12 format, the server's exact behaviour on a client FIN, what a real server does when ACKs stop. UDP stream defaults were never used on a real network; the `window`/`mtu` the client announces (1 MiB / 1500, so 699 datagrams in flight) is a choice, not the reference client's 42 MiB.

HAND-OFF: register `SoapyRemoteSource` under driver key `soapyremote`; args string `soapyremote=host[:port],prot=tcp|udp,device=key:value;key:value,timeout=ms`; one reader thread (the base class's, R_DRIVER); strings the screen needs: "SoapyRemote server address", the stream protocol choice (tcp default), the device-args field, the sentences in `lastError()` (connect refusal names the server and the SoapySDRServer hint). `NetSampleSource::readersAbandoned()` is the counter for the health row.

## Part 3: R3 SDRconnect WebSocket client

Files: `src/source/websocket_client.{hpp,cpp}` (RFC 6455 client pieces: SHA-1, Base64, handshake, frame encoder, incremental frame parser), `sdrconnect_protocol.hpp` (the API's messages), `sdrconnect_source.{hpp,cpp}`, test `tests/test_sdrconnect_source.cpp`. No new thread: the base class's reader (already in the thread inventory).

**Documents.** SDRplay's own PDF "SDRconnect WebSocket API", https://api.sdrplay.com/docs/SDRconnect_WebSocket_API.pdf, 6 pages, version 1.0.3 (the document's own `api_version` example), author in the PDF metadata "Andy Carpenter", fetched and read in full on 2026-11-11 (text extracted from the PDF's content streams by a short script written for the purpose; the fetch tool returned only metadata). The page https://sdrplay.com/websocket-api (from the re-check) states no licence; the document has a copyright footer only; SDRplay's terms for the document are NOT VERIFIED beyond that. The C# and JavaScript example links were not opened. The WebSocket layer is RFC 6455 (IETF, freely readable): sections 1.3, 5.2 to 5.5 and 5.7's worked examples are test vectors; SHA-1 from FIPS 180 test vectors and Base64 from RFC 4648 vectors.

**What the document gives, and what is built.** JSON text messages with string fields `event_type`, `property`, `value`, optional `device`; pushes `property_changed` / `get_property_response`; requests `set_property`, `get_property`, `iq_stream_enable`, `device_stream_enable` and the device selectors (`selected_device`, `selected_device_serial`, `selected_device_name`; the serial form takes `serial:network mode`, "Full IQ", "IQ Lite" or "Compact" being the three names the PDF lists). Properties used: `api_version`, `device_sample_rate`, `device_center_frequency`, `lna_state` (+ `_min`, `_max`), `valid_antennas`, `active_antenna`, `valid_devices`, `active_device`. Binary frames: little-endian u16 payload type then signed 16-bit interleaved IQ. open(): handshake, `api_version` (the proof it is SDRconnect), optional device selection, read-back of the rest. start()/stop(): `iq_stream_enable` and `device_stream_enable` true/false. Each control is a request followed by a `get_property` read-back, because the document defines no acknowledgement for `set_property`. The one LNA control is offered as "LNA state" in STEPS (the document gives states, not decibels). Audio, spectrum, recording, the secondary tuner and device profiles are not used.

**NOT in the document, so not guessed (build as far as it goes):**
* The TCP port and the WebSocket path. The default port 5454 is from a search snippet in the re-check (NOT VERIFIED); the path defaults to `/`. Give the port explicitly until verified.
* The IQ stream's sample rate. The client reports `device_sample_rate`; whether the stream is decimated (an "IQ Lite" mode suggests it may be) is unknown.
* Sample scaling (divided by 32768) and I-then-Q order ("IQIQ").
* **The binary type numbers.** The re-check note recorded them as 0 audio, 1 IQ, 2 spectrum; the PDF as read in this lane numbers them 1 audio, 2 IQ, 3 spectrum (primary) and 4, 5, 6 (secondary), page 6 table. The code follows the PDF as read in full and holds the numbers in one place (`kBinary*` in sdrconnect_protocol.hpp): a real server that disagrees is a one-line fix.

**UNPROVEN.** Everything against a real SDRconnect. The stand-in is written from the same reading. It has its own frame writer/reader; its accept value uses the client's SHA-1/Base64, which are proven against the standards' vectors in the same test.

**Behaviour notes.** TCP read in 200 ms slices (as part 2: a close is noticed within a slice whatever the peer does with a FIN). A streaming source silent for `max(3, timeout/200 ms)` slices latches a fault. Server pings are answered with pongs; a server close frame is a fault ("SDRconnect closed the connection"); a masked server frame, reserved bits or opcode, a fragmented control frame, an oversized length, or a data frame inside a fragmented message is a fault with the violated rule in the sentence. Extensions or subprotocols in the reply refuse the connection (none was offered). Bytes that arrive in the same write as the handshake reply are kept.

HAND-OFF: register `SdrConnectSource` under key `sdrconnect`; args `sdrconnect=host[:port],path=/,serial=...,mode=Full IQ|IQ Lite|Compact,name=...,index=N,timeout=ms`; one reader thread (base class); screen strings: server address with port, optional device serial / name / index, network mode names, "LNA state" step control, the lastError sentences (handshake refusal names the rule; "this is not an SDRconnect WebSocket server" when `api_version` is unanswered).

## Part 6: R9 RSPduo dual-tuner, source level

**UNPROVEN on a real RSPduo**; every record in the tests is hand-built. Also not done, as the brief says: no combiner, no second stream, nothing in `SdrPlaySource` (its `streamCallbackB` still drops channel B on purpose).
