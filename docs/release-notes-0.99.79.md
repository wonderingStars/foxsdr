## Features and fixes, 2026-10-14

**A message from the FoxSDR team is shown to every copy whose Updates tick is on, whether or not there is an update, until its Seen key is pressed.** The owner's request on 2026-10-14: "the broadcast system for the software should send the broadcast out even if there isn't an update; it should post to the user, then they click Seen and it doesn't show up again". The website's broadcast (a few lines written when something is wrong with the software or the service, or when nobody is there to answer) rode inside the release notes of an update, and the application drew it only in the update banner, which exists only when a newer build does. From website 2.77.0 the answer to the update check carries the broadcasts as a list of their own, `messages` (an id, a date, one or more lines, and the owner's "Important" tick), for a copy on 0.99.79 or newer, and the application draws a card for each message it has not been told is Seen, above the update banner and independent of it: **Not now** on the banner does not hide a message and **Seen** does not dismiss the banner. Pressing **Seen** puts the message's id in `config.json` on this computer (`messagesSeen`, at most 50, the newest kept) and saves it at once; nothing is sent, so the website cannot tell which messages anyone has read. An id the next successful check no longer carries is forgotten, so a message the owner withdraws and later sends again is shown again, and a failed check changes nothing. SYSTEM → Updates says how many unseen messages are waiting. What is accepted from the answer is bounded: at most 10 messages, 20 lines each, a line clipped to 1,000 bytes on a character boundary and a date to 32; an entry whose id is not 1 to 40 letters, digits, `_` or `-` (the id is written into the settings file), or that has no line of text, is dropped on its own without refusing the manifest or the messages beside it, and a field of the wrong type never throws. For tests, `FOXSDR_FAKE_UPDATE_MANIFEST=<file>` makes the check read a file instead of asking foxsdr.com (the fetch refuses anything that is not https, so a stub on a loopback port cannot stand in for the site), and logs one line that says so, never the path or what the file said. Three new strings (the card's heading, the key, the section's count) are translated in all 33 catalogues.

Checked on Windows: all 374 tests pass in one job (2,704 s), among them `test_updater` with 322 checks (26 of the 294 that could run failed red against stubs first), `test_config` with 3,566 (7 failed red first), `test_i18n` with 196,583, `test_store_update_app` with 51 (its unpackaged run still takes the foxsdr.com path), and the new real-program test `test_team_message_app`, 65 checks over fourteen runs of the real application of 70 frames each against a canned answer: a message and no update draws the card and its key and no update banner, one press of Seen writes the id into the settings file and the next launch on that file draws no card, an id the answer no longer carries is forgotten and one it still carries is kept, an important message is drawn as important, a message with an update draws both, an unticked box asks nothing and draws nothing, a Microsoft Store copy reads no canned answer, and with two messages each Seen key leaves exactly the other card (`test_team_message_app` was last changed, to add the Microsoft Store run, after the full run; it then passed five times alone). Each new behaviour was removed once and its test went red: 15 removals (the card, the Seen append, the prune, the settings save, the equality check, the per-card id, the section line, the id charset, the ten-message cap, the twenty-line cap, the character-boundary clip, the "only with an update" condition, the repeat filter, the newest-kept cap, the canned-answer seam), listed in the commit message. On a 1920 x 1080 screen in the default theme the card was looked at once: red heading for an important message, amber for another, the date, wrapped bullet lines, a full-width Seen key. **Not verified: the website side** - site 2.77.0 is not published, so no real answer has carried `messages` yet and every Windows run used the canned file; **and any of it on Linux**, where the new code is standard C++ and the test's POSIX branches are copied from the existing real-program tests, but nothing was built or run there. A manifest refused for its download fields (a missing checksum, a URL off foxsdr.com) carries no messages either, because they ride the same answer.
