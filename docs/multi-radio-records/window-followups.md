## CRASH (item 10, review B2)
Report: `D:/foxsdr-build/look-review/crash-report-s3-clips.txt`; reproduced with the review's own script (`scripts/en-s3-clips.txt`, copied to `wf-scratch/scripts/crash-s3*.txt`).
Runs on THIS build (860fbc65 + edits so far), the full 2400-frame script, with its `shot` steps:

| Window | Runs | Faults |
|---|---|---|
| 1600 x 2200 | 4 | 0 |
| 1600 x 4400 | 4 | 2 (exit -1073741819, access violation) |
| 1600 x 6000 | 3 | 0 |
| 1600 x 8000 | 6 | 3 (exit -1073740771 twice, -1073740791 once) |
The short script (the `type`, `shot`, `enter` lines only, 160 frames): 0 of 6 at 8000 and 0 of 6 at 4400: the fault needs the full script's state (a running clip recorder) as well as the tall picture.
STACK of a kept report (`wf-scratch/tmp/foxsdr-slint-drive-crash-s3-8000-*/diag/crashes/`, resolved with the build's own PDB through dbghelp, `wf-scratch/sym.py`): the access violation is inside `slint_cpp.dll`, in a walk of the item tree that goes `Component_rectangle_5179::visit_children` (the sections list's repeated component of `MainWindow`) -> the toolkit's `slint_visit_item_tree` -> `MainWindow::visit_dynamic_children` -> the same component again, to the depth the report records. The window toolkit's own frames are the top of every stack; no FoxSDR frame is the cause (the exe frames are only generated `visit_children` trampolines).
DECISION: the fault was seen only in windows 4400 px tall or more, with a picture taken (`take_snapshot`, used by the drive's `shot` and by the product's screenshot key) and the clip recorder running; none in 4 runs at 2200 px. No screen is that tall (an 8K screen is 4320 px; Windows clamps a window to the work area unless the application asks for more, and this one's drag edges cannot ask for more than the screen). So it is NOT a user path: the limit is a window taller than 4320 px. GUARD: the bounded run says so in one plain sentence when a script takes a picture in a window taller than 4320 px (`tallShotWarning`, `host_logic.cpp`, tested). It is a WARNING, not the refusal the brief offered: 19 committed drive scripts take pictures in windows 4400 to 8000 px tall (`e1-web-secure`, `lanek-backup`, `lanek-tools`, `lanel-*`, `lanem-*`, `lanex-bench`, `s1-signal-*` ...) and refusing them would fail the gates. PROOF GAP: the root cause inside the toolkit is not found (a debugger on slint_cpp.dll was not available); "only tall" is evidence of 2200 px clean and 4400 px faulting, not a proof that no height below is unsafe. OPEN ROW: shorten those 19 scripts' windows or take their pictures in pieces, then turn the warning into a refusal.
