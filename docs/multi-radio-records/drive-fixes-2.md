## Owner reports (nothing changed)

**Decoder output / preset wakes every decoder.** The window reports FOXAPP_PLUGIN_USE_DECODER_OUTPUT for EVERY decoder plugin while the Decoder output window is open (`kit_logic.cpp pluginUseText` line 533: `open.decoderOutput && caps & (DECODER | IQ_DECODER)`), and the engine wakes every AUTO plugin that signal names (`engine_plugin_run.cpp` 403, `core/plugin_run.hpp` decoderOutput). Smallest change: in `pluginUseText` set the bit only for the plugins whose lines the window will show: the one whose preset (or window) was opened plus the ones pinned to Always, e.g. an `OpenWindows::decoderOutputFor` name set fed from the preset press (`kit_publish.cpp` 214 to 231) and the pins. What would stop working: the Decoder output no longer shows "whatever hears this channel" from every fitted decoder at once (a person tuning to 931.9375 MHz and watching which decoder answers sees only the chosen one and the pinned ones), and a plugin woken only by that window (nearby-signal catch style) stays asleep until pinned.

**A busy radio writes a new "busy" failure message every few seconds.** The retries are bounded by `engine/saved_radio_retry.hpp`: after the failure at start-up a BUSY saved radio is tried at 2, 4, 8 and 16 s and then no more, so one start makes at most 5 radio_fail messages (the 4 files in about 20 s part 06 saw were these); a hot-plug arrival resets the count while a retry is waiting (`engine_hotplug.cpp` 57), so a USB event can add 4 more. The reporter's daily bound is 100 radio_fail a day, the first of each distinct (radio, class) of the day always passing (`core/radio_reporter.hpp` 147 and the header, lines 12 to 14), the queue folder 200 files / 4 MiB / 14 days. So one stuck radio makes 5 per start of FoxSDR (about 10 a day at a few starts) and can never send more than 100 a day.

**A failed saved radio is rewritten to the signal generator in the saved settings.** By design it is NOT rewritten at exit: the failed restore keeps the saved radio (`restoreKeep_`, `core/tune_control.hpp` 1786 to 1840, `sourceToSave` 1886: while the live source is the generator and something is remembered, the save writes the remembered radio, args and rate), and only a deliberate pick of the generator overwrites it (`engine.cpp` selectSource idx 0). Part 06's profile showing `siggen` is therefore NOT what this code writes for a radio with args; I could not reproduce it (no radio opened by this lane), so which save wrote it is UNVERIFIED (a mid-run settings write with `restoreKeep_` empty, or the config being read before the retry, are the places to look). Does the saved radio come back when plugged in again? On the next start, yes (it is tried again). In the same session only for a BUSY failure: the hot-plug arrival resets the retry (`engine_hotplug.cpp` 53 to 58, `savedRadioRetryBusy_` is set only by a busy failure); for an ABSENT radio (unplugged) nothing retries it in the session: the Source list shows it as the saved radio and the person presses it.
