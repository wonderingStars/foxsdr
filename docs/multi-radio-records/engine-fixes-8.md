## D3. Airspy HF+ will not open on Windows (RELEASE BLOCKER) - commits cbc154e7, 9be74061
* Cause, read in the code before believing it: `readCalibrationLocked` (`src/source/airspyhf_source.cpp`) pushed the flash's crystal trim (request 17) and front-end options (request 18) back with `controlOutLocked`, which marks the device dead on any failed transfer (`noteTransportFault`: "the radio stopped answering while <step>: ...; unplug it and plug it back in"). The reference library ignores both results.
* RED, reproduced with the fake transport the source's tests use (`failingRequests = {17}` and `{18}`): `open() with request 18 refused said: the radio stopped answering while restoring the frontend options: fake: the device is gone; unplug it and plug it back in`, `test_airspyhf_source: 421 checks, 8 failed` (the user's sentence, for the stated reason).
* Fix: `optionalControlOut` (the OUT twin of `optionalControlIn`); a refusal of either write is logged ("the receiver refused to take back its stored crystal trim; carrying on without it") and the open carries on; the flash's calibration is still applied to the tune. GREEN: `test_airspyhf_source: 421 checks, 0 failed` (section 16b: 17 refused, 18 refused, and SET_SAMPLERATE refused still fails the open).
* Break-it: the RED run above is the break-it (the same test against the old `controlOutLocked` path); the fix restored gives GREEN.
* Other optional writes found (list, none changed): every other OUT request goes through `controlOutLocked`: SET_RECEIVER_MODE (start, stop, quiesce), SET_FREQ, SET_SAMPLERATE, SET_ATT, SET_LNA, SET_AGC, SET_AGC_THRESHOLD and SET_BIAS_TEE (bias tee only when the board reports one). At open the driver sends SET_SAMPLERATE, SET_ATT(0), SET_LNA(false), SET_AGC(false), SET_AGC_THRESHOLD(false) and, if supported, SET_BIAS_TEE(false). None is shown to be refusable on a working receiver, so none was changed (that needs the device; see the open rows).
* Classification: `classifyRadioOpen` had no rule for the sentence, so the fault was counted `radio_fail.airspyhf.other`. New `RadioReason::Control`, word `control`, for "control transfer" or "stopped answering while" (after the timeout, busy, bind and sample-rate rules, so those still win). Vocabulary +14 fail tokens (220 to 234); `PRIVACY.md` table, `telemetry-worker/worker.js` list and the token-count test updated. `test_health_events`: two new cases (the HF+ sentence, a HackRF step), 114874 checks, 0 failed; break-it (rule disabled) 2 failed, restored 0 failed; `test_health_paths` Passed; telemetry worker tests 67 of 67. The per-failure report is NOT built (separate work).
* **UNVERIFIED on a real receiver: there is no Airspy HF+ on this desk. The fix is proven against the fake transport only.**

## D1. The scanner's "Priority MHz" field never reached the engine - commit 3b86f68c
* The field and "Every s" were stored and never sent; the "not used yet" note hid once `fact.scanner.extras == "1"`. RED (send removed): drive script `lanec-scanner` reads the engine's own `fact.scan.priority` through the new state key `lanec.enginepriority`: `state lanec.enginepriority == 162550000.000;121500000.000 -> FAILED: it is ` (empty), and the note stayed on.
* Fix (`lanec_*` only): `PriorityPush` (`lanec_logic`) and `LaneCPublisher::tick` send SCANNER_EXTRAS 0 at start-up from the saved list (an empty saved list sends nothing, so the engine keeps its persisted list) and whenever the list or interval changes (clearing sends the empty list). The note is true only while the engine does not hold what the window holds. GREEN: `slint_drive_lanec-scanner` Passed; `test_slint_lanec_host` 2582 checks, 0 failed. Break-it: that RED run (send replaced by a no-op), restored GREEN.
* Not sent from the window and still stored only: the per-memory threshold (`Memory::thresholdDb`) and the lock-out list; see D2 and the open rows. The note still shows for memory thresholds while the engine reports no extras.

## D2. Range-scan lockouts - verified, NOT fixed
Verified by reading `lanec_publish.cpp` and the drive script `lanec-lockout.txt`: the window sends lockouts only for a scan of the ticked rows (it unticks the bookmark, `FOXAPP_OP_BOOKMARK_TICK`); for a range or plan scan the keys are DISABLED (`lock_enabled` needs `fact.scanner.listMode == 1`), and `FOXAPP_OP_SCANNER_EXTRAS` 1 (lock a frequency out), 2 (clear) and 5 (the configured locked list) are never sent by any window file. So the keys do not look live for a range scan (unlike D1), but the engine's range-scan lockouts are unreachable from the new window. Not as small as D1: the window also needs the engine to say what is locked out and when a timed lockout ends (there is no fact for the runtime lockouts; `fact.scan.locked` is only the configured list from op 5), a status text, the keys enabled for range scans, and tests that make a scan skip a locked frequency. Listed in the open rows.
