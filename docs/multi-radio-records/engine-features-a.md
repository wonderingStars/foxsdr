## Task 2. `test_engine_api_transmit`: the verdict

**What it measures.** `testTicketBooksUnderMerging` (the round-5 review's stress probe) sends random batches of PTT / latch / run / consent / volume commands for 3000 loops while another session stalls the control thread for random 0 to 39 ms; it asserts the ticket BOOKS (every new ticket gets one result; no result names an unknown ticket; tickets and results only increase; NO_CHANGE never names a ticket already read) and, as a COVERAGE guard, `issued.size() > 1000` new tickets.

**Why the number moves.** A session may have only `FOXAPI_MAX_PENDING` (256) ordinary commands outstanding. While the staller holds the control pass, an ordinary command (5 in 9 of the probe's commands) is answered BUSY and gets no ticket. So how many NEW tickets 3000 loops earn is a figure about how fast the control thread drains against how fast the test thread submits: it depends on machine load, not on the code. Measured with the UNCHANGED test:

| Run | New tickets | Merged | Refused BUSY (derived) | Books |
|---|---|---|---|---|
| quiet machine, run 1 | 1723 | 4601 | about 4,200 | all zero |
| quiet machine, run 2 | 1717 | 4605 | about 4,200 | all zero |
| 24 CPU burners, run 1 | **523** (red: `issued.size() > 1000`, line 1500) | 4625 | | all zero |
| 24 CPU burners, run 2 | 1538 | 4605 | | all zero |
| the wave 3 and stage 7 records, the other lanes building | 802 | | | |

In every run, including the red ones, the books themselves held. "Half to always" is the load of the other lanes' builds, not a commit: the test file has not changed since 2026-10-21, and the code it measures (the merge rule, the 256 cap, the pass) is the same on the merged tree and the stage 5 and 6 tree that failed identically.

**Outcome: the expectation was wrong, not the code.** The guard says "the probe exercised the books on enough tickets", which must hold whatever the machine's speed; a fixed loop count cannot promise it. The probe now runs at least 3000 loops and then goes on until it has issued 1500 new tickets, or fails with the figures after 120 s (an engine that does not drain). The `> 1000` assertion, `merged > 1000` and every assertion about the books are unchanged; nothing was loosened. The loop now yields now and then after a BUSY instead of hammering a held pass. The summary line prints the BUSY count and the loop count.

**GREEN.** With the fix: 1538 and 1653 new tickets (3000 loops, 4189 to 4302 BUSY) in the two runs under the same 24 burners that gave the red 523 with the old test; {{TX20}}. ## Task 3. The TCI server and audio over the network (design section 8)

**Sources read, in this session.** TCI Protocol 2.1: `https://github.com/ExpertSDR3/TCI`, file `TCI Protocol 2.1.pdf` (fetched from `https://raw.githubusercontent.com/ExpertSDR3/TCI/main/TCI%20Protocol%202.1.pdf`, 735 KB, about 50 pages; read in full through `pdftotext` on the saved file). Licence: the MIT licence, printed on the PDF's front page ("Copyright (c) 2023 \"Expert Group\" LLC, Taganrog", the usual permission and warranty text) and named by the repository's `LICENSE`; the notice must be kept in copies of the document, and none of the PDF's text is copied into this tree (a command grammar and command names are what interoperability needs). The document's own date line says "September 2026" and its version table lists 2.1. **The PDF names no default port**: 50001 is what the facts report found other programs using, kept as the default and recorded as such. RFC 6455 (`https://www.rfc-editor.org/rfc/rfc6455`) for the WebSocket layer; FIPS 180-1 and RFC 4648 test vectors for the SHA-1 and base64; GQRX's page `https://gqrx.dk/doc/streaming-audio-over-udp` for the UDP format (from the facts report; not re-read).

**The WebSocket question.** The vendored cpp-httplib 0.53.1 DOES contain a WebSocket server (`Server::WebSocket`, `ws::WebSocket`) and client (`ws::WebSocketClient`): proved by compiling and by running its client against this lane's server (`test_tci_server`, 238 checks). It is NOT what the server runs on, for reasons read in its source: one blocking thread per connection with a blocking read; `send` waits on a client that never reads (up to the socket's write timeout, holding the write mutex); `close()` reads the stream from a second thread; its heartbeat closes the same way; and on Windows its listener option is `SO_REUSEADDR` (no `SO_REUSEPORT` there), which lets a second program bind a port already in use. A control port that must drop a slow client without waiting for it and say "port in use" in words is simpler to get right as a polled loop over a small RFC 6455 layer (`net/ws_frame.*`, 330 lines, SHA-1 and base64 included, written from the RFC; no new third-party code). Its client, however, is a second, independent implementation of the RFC, which is exactly what the tests need. Also noted: httplib's WebSocket client's `set_read_timeout` does not bound a read after the connection is up (a read for a message that never comes blocks for its 300 s default), which is why the tests read only for messages that must arrive.

**What was built** (all under `src/net` and `src/engine`):
* `ws_frame` (handshake checks of RFC 6455 4.2.1, frame codec, fragmentation, control-frame rules, masking, close codes, UTF-8; at most 8 KiB of request head, `maxMessage` payload bytes buffered, a frame that DECLARES more is refused before its payload is read).
* `tci_protocol` (pure: the grammar, the receivers, the state machine, the audio packer, a windowed-sinc decimator for 24, 12 and 8 kHz). Subset spoken: the initialisation commands in the specification's order then `READY`; `START STOP DDS IF VFO MODULATION RX_ENABLE RX_FILTER_BAND SQL_ENABLE SQL_LEVEL`; `TRX TUNE TX_ENABLE` always `false`; `AUDIO_START AUDIO_STOP AUDIO_SAMPLERATE AUDIO_STREAM_SAMPLE_TYPE AUDIO_STREAM_CHANNELS AUDIO_STREAM_SAMPLES`; the receiver audio stream with the 64-byte header. Everything else is ignored without a reply (the specification's rule for an unknown command).
* `tci_server` (acceptor; one polled non-blocking thread per client; at most 4 clients; sends into a bounded queue; a client that accepts no byte for 3 s or lets 1 MiB queue is dropped; audio is not read for a client with 256 KiB waiting).
* `udp_audio` (raw 48 kHz S16LE mono, 480 or 960 samples a datagram, 127.0.0.1:7355 by default).
* `server_host`: `SERVER_CONFIG` gained `"tci"` and `"udp"`, reconciled on the host's worker; `InternalKind::Tci` (six ops: `RUN SET_CENTRE SET_VFO_OFFSET SET_MODE SET_BANDWIDTH SET_SQUELCH`; grants TUNE, SETTINGS, AUDIO; REMOTE flag) and `InternalKind::Udp` (AUDIO only, no op); `ApiHost::readAudioOfRadio` (the audio of any named radio for a session that serves several: one TCI session serves every radio). Three new threads in the inventory (`tci-accept`, `tci-client`, `udp-audio`).
* Settings keys `tciEnabled tciBindAll tciPort udpAudioEnabled udpAudioHost udpAudioPort udpAudioRadio udpAudioPacketFrames` (clamped on read: a hostile value goes back to the safe default, never to something wider). API.md 6.22 and `api-0.3-additions.md` 9.24; PRIVACY.md's thread list.

**Op numbers taken.** None for TCI and UDP (they ride `SERVER_CONFIG`). Timed recordings, in the application-op group 0x86xx (beside the markers, next free after 0x860B): `FOXAPP_OP_SCHEDULE_SET` 0x860C, `_REMOVE` 0x860D, `_ENABLE` 0x860E, `_RUN_NOW` 0x860F, `_SKIP` 0x8610, `_FROM_HINT` 0x8611. The receiver-group numbers 0x0113 to 0x011F were not touched. No list id was taken (the schedule is read as facts).

**Safety defaults, each with the test that holds it** (the break-it column is in the table at the end):
* BOTH OFF BY DEFAULT: `testOffByDefault` (a fresh engine listens on nothing; `fact.tci.enabled` 0, `fact.udp.enabled` 0, the settings defaults).

**Facts read from the engine** (all LOCAL): `fact.tci.enabled .bindAll .port .listening .boundPort .scope .refusal`, `fact.udp.enabled .host .port .radio .packetFrames .sending .refusal`, and at the call `fact.tci.clients .commands .accepted .audioPackets .slowDropped`, `fact.udp.sent .errors`. `FOXAPI_LIST_SERVERS` stays two entries (departure from the design, which wanted four: an interface that counts them is not surprised; the screen can read the facts).

**Departures from the design.** (1) A WebSocket layer of our own rather than httplib's (above; the design said to prove the httplib claim "by compiling, or say what is used instead": proved, and said). (2) The list `SERVERS` stays at two entries; facts instead. (3) No I/Q stream and no `RX_SENSORS` (the design said "unless clients need it"; FoxSDR has no calibrated dBm scale and a made-up number would be a false reading; both are ignored without a reply). (4) The 200 ms monopolisation rule of section 3.5 of the specification is not implemented (a client's set is applied; the echo goes to everyone on the next tick). (5) `RX_ENABLE` follows the radio's running state, so receiver 0 can read `false` (the specification says the first transceiver is always enabled). (6) Receiver numbering is the index into the radios the engine has, ascending, and shifts when one is added or removed (the server says so). (7) `WFM` and `DSB` are FoxSDR's own modulation names: the specification names no wide-FM or double-sideband mode.

**UNVERIFIED (task 3).** No real TCI client was run (the owner has no verified one): WSJT-X, JTDX and Log4OM's behaviour against this server is unknown, in particular: the READY-before-state order (read literally from sections 3.1 and 4.1); what a client does with `RECEIVE_ONLY:true`; the meaning of `Stream.length` for a two-channel audio stream. **The specification is ambiguous there**: section 3.4 says `length` is "the number of real samples" in `data[]` (so frames x channels), while the recommended packet sizes in 4.3 are only consistent with `AUDIO_STREAM_SAMPLES` counting frames per channel (512 samples = 10.7 ms at 48 kHz; 16384 = 2048 x 2 x 4 is exactly `data[16384]`). The packer puts frames x channels in `length`, and splits `AUDIO_STREAM_SAMPLES` between the channels; for MONO the two readings agree, so a client that asks for one channel is safe, and a stereo client is the first thing to check against a real one. The audio of a real radio was not listened to. The UDP stream's consumers (aplay, multimon-ng) were not run. The WebSocket layer was proved against httplib's client only.

## Task 4. Timed recordings (design section 4), engine side

**What was built.** `core/schedule` (pure: the entry, validation, overlap, and `Runner`, a clock that takes time as an argument) and `engine/engine_schedule.cpp` (once a pass the clock's decisions become the commands a person would give on that radio: `SET_FREQUENCY`, `SET_MODE`, `SET_BANDWIDTH`, `RECORD_AUDIO`, `RECORD_IQ`, and back). Disk work stays on the recorder's worker: nothing here touches a file. Entries (at most 32): name, radio 1 to 8, UTC start, length 1 s to 24 h, once / daily / weekly (elapsed time, so a daylight-saving change moves the local hour; the display's business), optional tune (frequency, mode, bandwidth), audio and / or I/Q, "return to where I was", enabled. Saved in the settings file key `schedule` (written only when there is an entry; an older reader ignores it).

**Rules the clock keeps** (each has a pure test and an engine test): a start is at most 30 s late and then runs; later than that it is MISSED (counted, shown, never run late); an occurrence is handled once, remembered in `lastStartUnix` (saved), so a restart neither replays nor recounts, a clock set back never re-runs one; a recording ends `lengthS` after it began, or at once when the clock is set back by more than 2 s (a back-step under 2 s goes on); a forward jump over a start misses it and over a whole recording ends it; removing, disabling or moving an entry to another radio ends its recording; an entry whose radio is closed, stopped, still opening, already recording (by hand or for another entry) or held by the scanner is refused in words and the occurrence used up (nothing is ever taken over; a hand recording is not stopped by the schedule); two enabled entries on one radio may not overlap (compared over the next two weeks; back to back is fine); a recorder that cannot open its file (an unwritable folder) is found out a few passes later and refused with the recorder's own sentence, the other recorder stopped and the tuning put back.

**Op numbers**: `FOXAPP_OP_SCHEDULE_SET` 0x860C (long text JSON, `ival[0]` 0 add / id replace, `applied[0]` the id), `_REMOVE` 0x860D, `_ENABLE` 0x860E, `_RUN_NOW` 0x860F, `_SKIP` 0x8610, `_FROM_HINT` 0x8611 (below). All LOCAL only. **Facts** (LOCAL): `fact.schedule.count .active .missed .max .next`, `fact.schedule.entry.<id>` (one JSON document: the fields plus `state` waiting / starting / recording / done / stopped early / missed / refused / skipped / disabled, `note`, `nextUnix`, `lastStartUnix`, `missed`), `fact.schedule.hint.count` and `fact.schedule.hint.<n>`. **Test hook**: `SETTING_SET test.scheduleClock=<unix ms>` (testHooks engines only). ### The plugin hand-off (what the satellites lane must call)

Built here: the additive host call only. `plugin_abi.h` (src/core copy) gained, before `CascadeHostApi`, `CASCADE_SCHEDULE_LABEL_CHARS` 32, `CASCADE_MAX_SCHEDULE_HINTS_PER_PLUGIN` 16, `CASCADE_SCHEDULE_HINT_PASS` 1 and

```c
typedef struct CascadeScheduleHint {
    uint32_t structSize; uint32_t id; uint32_t kind; uint32_t demodMode;   /* CASCADE_DEMOD_*; 0 = leave */
    int64_t aosUnixMs; int64_t losUnixMs;   /* losUnixMs after aosUnixMs, at most 24 h; dates 2020..2100 */
    double maxElDeg;     /* 0..90 */
    double freqHz;       /* above 0, below 6 GHz */
    double bandwidthHz;  /* 0 = leave; at most 20 MHz */
    char label[32]; char decoderName[32];
} CascadeScheduleHint;
```

and, APPENDED at the end of `CascadeHostApi` after `settings_seq`: `int32_t (*set_schedule_hint)(void *ctx, const CascadeScheduleHint *hint);` and `int32_t (*clear_schedule_hints)(void *ctx);`. **The plugins repository's `include/plugin_abi.h` must be made byte-identical** to this tree's `src/core/plugin_abi.h` (take the file; `git diff 08320a72^ 87d83583 -- src/core/plugin_abi.h` is the whole change). The host API LEVEL is not bumped (the design said 3; the header's rule is that the struct size is the version, and `test_tx_audio` pins level 2); a plugin tests `CASCADE_HOST_HAS(host, set_schedule_hint)`. **What the satellites plugin must call**: after each TLE refresh and each hour, run `passes.h` over the tracked satellites for the next 24 h and for each of the next 16 passes call `host->set_schedule_hint(host->ctx, &h)` with `id` its own stable number for the pass, `kind` `CASCADE_SCHEDULE_HINT_PASS`, `aosUnixMs`/`losUnixMs` from the pass, `maxElDeg`, `freqHz` the downlink, `demodMode` and `bandwidthHz` as the plugin's table states, `label` the satellite's name and `decoderName` the plugin the user would want ("lrpt-decoder"; informational: the host does not start decoders); `clear_schedule_hints` when it stops tracking. The host copies everything, replaces by id, refuses with a result code a bad hint, and forgets a plugin's hints when it stops. A hint does nothing by itself: the user picks one (`FOXAPP_OP_SCHEDULE_FROM_HINT`, hint number from `fact.schedule.hint.<n>`, radio), which makes an ordinary entry from one minute before the pass to one minute after, tuned, I/Q recorded, tuning put back. UNVERIFIED: how the satellites plugin learns which satellite is "tracked" when the host starts it. Meteor LRPT is the design's first (APT untouched); the plugin must not claim a pass is live.
