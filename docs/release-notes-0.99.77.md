## Features and fixes, 2026-10-13

Six changes were made on 2026-10-13, after 0.99.75 was published: the display-range menu, the guard for the page grip's resize-corner id, the reading of a Linux scan helper's closed pipe, the grouping of the plugin lists with the two clicks beside it, the pressable panel row, and the handling of an old copy of a plugin whose name changed between versions. The first three were built together as 0.99.76 and its CI passed, but it was not published; the other three came after it, and 0.99.77 is the first published release with any of the six. The first answers a dislike from the field, the second a fatal crash report, the third two crash groups from one Linux session, the fourth and fifth answer US testers, relayed by the owner, and the sixth a US tester's screenshot of two TETRA sections and an ImGui error box, sent the evening the release was being built. The first three touch different parts of `src/gui/app_window.cpp` and `src/source/soapy_enum_proc.*` and applied together without a conflict. The grouping and the pressable row touch `src/gui/app_window.cpp` and `src/gui/plugins_view.cpp` in different places and applied together with one overlap: each had added the census line `panel:window:<plugin>` to the panel window's drawing, and it was kept once, with the second change's `panel:rows:<plugin>:<n>` beside it.

**For the crash admin: type 0.99.77 as the fix release, and no earlier number, for these three groups.** The fatal crash group `crash cascade.exe @ ImGui::GetWindowResizeCornerID` (fixed in 0.99.77) holds report `D94CCD4584724FAC` (0.99.58) and report `DE3F72AAE6B69997` (0.99.75); it was marked fixed on 2026-10-01 with no release named, and the second report is the one that reopened it. **Right-click the spectrum or the waterfall to set the range of the picture yourself: the menu now ends with a Display block - Range: Automatic or Manual, a Floor and a Ceiling slider, and Reset display to defaults - and the strength key says MANUAL while your own window is in force; hold the pointer still over either panel for four seconds and a tip says that the right-click menu is there.** A French user on 0.99.75 with an RTL-SDR V4 wrote that "the spectrum and the waterfall are very milky, one cannot see the signals", and the owner's answer was to let people set it themselves, by right-clicking. The window was always adjustable - SYSTEM > Display > Min dB and Max dB - but that section has been folded until opened since 0.99.74, and nobody with a milky picture had a reason to open it. The two sliders in the menu are the same two numbers, so either place changes both, and nothing in the signal path changed. The menu is on the receiver's waterfall (the marker menu), on its spectrum (the trace menu) and on a patch Spectrum part's picture and trace, the same block each time, after the items that were already there.

What Automatic and Manual are, because the two views meant different things by "automatic" before there was a word for it: the receiver's spectrum and waterfall have always been drawn through one fixed window, -110 to 0 dB, unless the sliders moved it, and that window is Automatic; a patch Spectrum part fits its own window to every line it draws (the 20th-percentile bin, which is the noise, up to the loudest bin, never under 30 dB), and that is Automatic there. Manual is your floor and your ceiling on all of them together, so the spectrum's scale, the waterfall's colours, the strength key and every patch Spectrum part agree about what a colour means. The ceiling stays at least 10 dB above the floor, and the slider you are dragging is the one that stops. Reset display to defaults goes back to Automatic, forgets the pair, and returns the spectrum to its normal trace. The choice is saved as `waterfallRangeMode` (`"auto"` or `"manual"`) beside the `dbMin` and `dbMax` that have always been in `config.json` (the floor and ceiling Manual uses, kept while Automatic is in force); a file with no mode, from 0.99.75 or earlier, opens in Manual if its pair is anything but -110 and 0 and in Automatic if it is, so nobody's picture changes. The waterfall keeps the colours it has already painted, as it always has when the sliders moved: after a change the key says "APPLIES TO" the newest lines and a "RANGE CHANGED" rule crosses the picture. Display > Min dB and Max dB now show the window in force, make the range Manual when dragged, and clamp a typed value (ctrl-click entry could exceed the slider's bounds before).

The tip is the owner's: "when the mouse is over it for 4 secs". After four seconds of rest over the receiver's spectrum or waterfall, or a patch Spectrum part's trace or picture, a tooltip reads "Right-click to change the range and display", in place of the panel's usual gesture tip while the hand stays still. Moving more than 6 pixels, pressing a button, dragging the band, panning, opening the menu or leaving the panel puts it away, and it comes back after another full four seconds. One related fix: a range exactly 10 dB apart is now kept. The sliders always allowed it and the config loader refused it, so a range left there was thrown away, both ends back to -110 and 0, at the next start. The remote control's own range check still refuses a request that names both ends exactly 10 dB apart.

Report `DE3F72AAE6B69997` (0.99.75, from a machine that had opened the WEFAX window five minutes earlier, and probably the one whose user filed a bug that day saying that inserting a window at the bottom with the mouse does not work) faulted at `GetWindowResizeCornerID+0x1b`, which in a build of the same source is the load of the host window's id; the 0.99.58 report `D94CCD4584724FAC` has the same two frames. The id is now asked of one helper, `gui/page_resize_id.hpp`, that answers 0 when there is no window or no host to ask, and a lit grip is no longer decided by 0 meeting 0 (the first version of the guard would have lit the grip and turned the cursor into a resize arrow in every frame that nothing was hovered). A new test, `test_page_resize_id` (22 checks), builds the windows ImGui builds in those frames; before the guard it faulted with 0xC0000005 on the null window, on a docked window with no node and on a docked window whose node has no host, and with the guard it passes; the guard was removed in four ways and each turned a named check red. Not reproduced live: the drop itself was not driven with a mouse, so that this is the report's path is a reading of ImGui's source and of the disassembly, not an observation. The application enables ImGui's docking but never creates a dock space over its main window (there is no `DockSpace` call in `src/`), so a page can be docked onto another page and not into the edge of the main window; that, read from the source and not tried with a mouse, is what this guards, and it is not an answer to the reporter's complaint that inserting a window at the bottom does not work.

**A Linux scan helper whose pipe has no reader is no longer filed as a crash, and no longer takes its driver out of the session's scans.** Reports `862234B08B9FC33D` and `30BCD594C128766D` (0.99.73) were six "crashes" from one Linux session in one second, every one exit `0x8D` = 141 = 128 + `SIGPIPE`, and the last blamed the `rtlsdr` driver alone, which put a working RTL-SDR on the do-not-ask list for the rest of the session. The helper now ignores `SIGPIPE`, writes through a function that learns of a closed pipe from the write itself and ends with its own exit code, 74, after finishing the walk; the parent reads 74, and 141 from a helper that did not ignore it, as a closed pipe: the scan is retried and swept and counted as before, but nothing is written to the crash directory and no driver is remembered. A real abort or segfault while the parent is listening is reported exactly as before, and a helper the parent timed out is still a timeout. Verified on Windows by 545 checks in `test_soapy_enum_proc`: the same scan run as a closed pipe and as a real death, whole-bus, retry and sweep, with 0 reports and nothing remembered against 1 report and 3 reports with the driver remembered; the old reading, put back, failed 12 of them. What a Windows run cannot show: the helper's own `SIGPIPE` handling and the 141 path are POSIX-only and were type-checked against stubs with GCC, not run, and the Linux run in CI is the check. What is also not established: the parent holds the helper's stdout open until it has reaped it, so a closed stdout was not the field's pipe while the parent was waiting; the helper's inherited stderr, or a socket in a vendor module, is the suspect, and `httplib::Server`'s constructor ignoring `SIGPIPE` for the whole process would make a helper started before the web server died where one started after did not. `docs/DIAGNOSTICS.md` lists the changed and new log lines.

**For plugin authors: what a plugin must do to use key rows, and the plugin that does.** The plugin ABI is still 3 and the host API level is unchanged (no `CascadeHostApi` member changed), and `docs/PLUGIN-API.md` has a new section, "Panel rows the user can press (0.99.77)". `plugin_abi.h` gains `CASCADE_ROW_FLAG_KEY` (`0x00000008u`), the command id in bits 8 to 15 of a row's flags (`CASCADE_ROW_KEY_ID_SHIFT`, `CASCADE_ROW_KEY_ID_MASK`, with `CASCADE_ROW_KEY_FLAGS(id)` to pack it, ORed with GOOD, WARN or MUTED, and `CASCADE_ROW_KEY_ID(flags)` to read it - a panel row has no size field to grow, so the id rides in the flags, as a track's category does), the state bit `CASCADE_STATE_ROW_KEYS` (`0x00010000u`, set in every `CascadeReceiverState` the host fills, with no grant) and `CASCADE_MAX_COMMANDS_PER_PLUGIN` 16 (it was 8). To use it a plugin reads `CASCADE_STATE_ROW_KEYS` from `get_state` and does nothing new unless it is set; when it is set the plugin registers the keys with `add_command` (ids 1 to 255), marks each row that should be pressable with `CASCADE_ROW_KEY_FLAGS(id)` for an id it registered, and takes the press with `poll_command` exactly as it takes a press on its plate. A plugin may say "press to choose" only when it has seen the bit, and should register the keys it can live without last, because a host before 0.99.77 refuses the ninth `add_command` with `CASCADE_API_LIMIT`. Junk left in bits 8 to 15 of a row that does not carry the flag is not read as a key. Both builders' copy of the new sentence beside the larger limit named `CASCADE_ERR_LIMIT`, which is not a name in the header; the integration corrected that one word to `CASCADE_API_LIMIT`, so the header is the application's `src/core/plugin_abi.h` with sha256 `045197df1e416ee8a02e1c641f2cd5844d355b22cdb5550a41e854d57956e75b`, and the plugin repository's `include/plugin_abi.h` must hold the same bytes (it does, as of the integration; the IBOC plugin repository's copy still has the old word until it is refreshed from the same file).

## Plugins on Linux

**41 of the 43 plugins in the catalogue now have a Linux x64 build and a Linux arm64 build, FT8 Decoder 1.1.1 among them; before 2026-10-13, 24 had an x64 build and none had an arm64 one.** This is a change to the plugin catalogue (commit `6f332d5` of the public catalogue), not to the application: the plugin store carries these builds, and nothing in the application's own files changed for them. Eleven x64 modules were rebuilt against glibc 2.35: three of them (AIS, EAS, Workbench) had been built against glibc 2.43 and could load on no current release of Ubuntu or Debian, and eight against glibc 2.38, which Ubuntu 22.04 and Debian 12 lack. FT8 Decoder 1.1.1, whose preset opens the Decoder output window and which says why it is silent, was published for Windows and Linux.
