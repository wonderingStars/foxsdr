## Features, 2026-10-13

Two changes were made on 2026-10-13, after 0.99.76 was published: the grouping of the plugin lists with the two clicks beside it, and the pressable panel row. Both answer US testers, relayed by the owner. They touch `src/gui/app_window.cpp` and `src/gui/plugins_view.cpp` in different places and applied together with one overlap: each had added the census line `panel:window:<plugin>` to the panel window's drawing, and it was kept once, with the second change's `panel:rows:<plugin>:<n>` beside it.

**The Fitted modules list and the DECODE bank's "Turn on and off plugins" list are now grouped under the store's own headings (AIRCRAFT, MARINE, SATELLITES AND WEATHER, METERS AND PAGING, VOICE AND DATA, MAPS AND TOOLS, OTHER), a double-click on a Fitted modules row opens that plugin's own window, and a click anywhere on a store card opens the plugin's page.** A US tester wrote, through the owner: "I really like how the store groups plugins by function (Aircraft, Marine, Satellites and Weather, etc). That really makes it easier to browse. Implement this sorting on the Plugins panel and the 'Turn on and off plugins' menu as well: if you install them all, the list is quite long, intermixed and kind-of alphabetical." The owner added: "when you open the plugins Fitted modules window, when I double click on the plugin it should show the plugin window", and "on the plugin store the whole [card] should be clickable not just the text of the plugin."

A module's heading is the catalogue's category for it, found the same way the Fitted modules window already found it for the module's drawing (the install record names the catalogue entry, the entry names the category), now by one function that both lists use so they cannot put a module under two headings. Inside a group the order is by name, as the store's grid is. A module the catalogue has not filed - one dropped into the folder by hand, or any module before a catalogue has been read or kept - is listed last, under OTHER. While no module has a category at all, as on a fresh install, there are no headings and the Fitted modules list is the name-sorted list it was; the DECODE bank keeps the order the plugin folder is read in. The chips and the search filter first and keep working, and whether there are headings is a fact of the whole list, so they do not come and go as someone types.

A double-click on a Fitted modules row, anywhere but on its keys, shows the plugin's own window: its panel if it has one, otherwise its picture window, its instrument or its map page. A dormant plugin wakes through the ordinary lifecycle as the window opens (`plugin: <name> woke - window open`, one decoder created, nothing pinned). Nothing is tuned: the rail's window rows also tune to the plugin's preset and this does not. A double-click on the name or the picture works too: the first click opens the module's page, as it always did, and the second press hands the user the window instead and brings the list back. A module with no window of its own (a text decoder, which is read in the shared Decoder output window) and a stopped one (with its instances gone no window of its could draw) get their module page, which says so and offers START. A single click is unchanged.

The whole store card is now one click target, submitted under the glyph, the name and the key so that those take the pointer where they are: a click on GET or UPDATE is the key's alone and never also opens the page. One thing is given up on purpose: a press that starts on a store card is a click on the card, so dragging the store window by a card's empty part no longer starts there (the gap between cards, the top bar and the rails still do; no test exercises it).

**A row in a plugin's panel can now be a key: where a plugin lists things to choose between, such as the IBOC Radio plugin's programmes HD1 to HD8, you press the row to choose it instead of going into the plugin's settings to type the number, and a plugin may now have sixteen command keys where it had eight.** A US tester, through the owner, asked for exactly this: "If I click on HD2 on the screen below, it should select that program, instead of having to go into the plugin settings and change the Programme to 1." The owner's answer was "can you implement this". The row lights under the pointer, the hand cursor shows, the cell texts stay as the plugin wrote them, and a plugin's green, amber and dimmed rows still read as they did. A press reaches the plugin the way a press of one of its keys in Fitted modules does, and only if the plugin has registered that key: a row that names a key the plugin never added is drawn as the text it always was, because a key that does nothing is a lie. A heading and a separator are never keys. A host older than 0.99.77 draws such a row as plain text and refuses the ninth key, which a plugin that reads the new state bit (below) never meets. The same rows beneath an instrument's face are keys too. The browser interface never carried a plugin's panel rows, so nothing changes there.

**For plugin authors: what a plugin must do to use key rows, and the plugin that does.** The plugin ABI is still 3 and the host API level is unchanged (no `CascadeHostApi` member changed), and `docs/PLUGIN-API.md` has a new section, "Panel rows the user can press (0.99.77)". `plugin_abi.h` gains `CASCADE_ROW_FLAG_KEY` (`0x00000008u`), the command id in bits 8 to 15 of a row's flags (`CASCADE_ROW_KEY_ID_SHIFT`, `CASCADE_ROW_KEY_ID_MASK`, with `CASCADE_ROW_KEY_FLAGS(id)` to pack it, ORed with GOOD, WARN or MUTED, and `CASCADE_ROW_KEY_ID(flags)` to read it - a panel row has no size field to grow, so the id rides in the flags, as a track's category does), the state bit `CASCADE_STATE_ROW_KEYS` (`0x00010000u`, set in every `CascadeReceiverState` the host fills, with no grant) and `CASCADE_MAX_COMMANDS_PER_PLUGIN` 16 (it was 8). To use it a plugin reads `CASCADE_STATE_ROW_KEYS` from `get_state` and does nothing new unless it is set; when it is set the plugin registers the keys with `add_command` (ids 1 to 255), marks each row that should be pressable with `CASCADE_ROW_KEY_FLAGS(id)` for an id it registered, and takes the press with `poll_command` exactly as it takes a press on its plate. A plugin may say "press to choose" only when it has seen the bit, and should register the keys it can live without last, because a host before 0.99.77 refuses the ninth `add_command` with `CASCADE_API_LIMIT`. Junk left in bits 8 to 15 of a row that does not carry the flag is not read as a key. Both builders' copy of the new sentence beside the larger limit named `CASCADE_ERR_LIMIT`, which is not a name in the header; the integration corrected that one word to `CASCADE_API_LIMIT`, so the header is the application's `src/core/plugin_abi.h` with sha256 `045197df1e416ee8a02e1c641f2cd5844d355b22cdb5550a41e854d57956e75b`, and the plugin repository's `include/plugin_abi.h` must hold the same bytes (it does, as of the integration; the IBOC plugin repository's copy still has the old word until it is refreshed from the same file).

**IBOC Radio (nrsc5 library) 0.1.1 is the first plugin to use it:** it registers HD1 to HD8 as command ids 11 to 18 only when the host sets the bit and only if the host takes all eight (so a 0.99.74 to 0.99.76 host, with its limit of eight, keeps the three keys it had: HD next, HD previous and Re-acquire), its PROGRAMMES rows become those keys with the heading "PROGRAMMES: press one to choose", and its dashboard picture says CHOOSE IN THE PANEL (the picture itself cannot be clicked). Without the bit the panel is exactly what 0.1.0 drew.
